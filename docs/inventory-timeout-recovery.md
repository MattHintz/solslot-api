# Inventory timeout recovery

`POST /protocol/native-purchases/inventory/reconcile-timeout` accepts only a purchase ID and requires the existing server token, minting-write ceiling and purchases operation gate. It observes an already executed timeout; it does not sign or broadcast a release. No request may supply its own chain evidence.

The reconciler reconstructs each exact reservation and timeout spend from the retained purchase artifact, signed bundle, item commitments and expiry. It requires a synced node on the purchase network, three confirmations, matching creation/spending heights, the exact canonical source spend and the matching timeout release (allowing only its uncommitted 32-byte buyer nonce), every unspent available successor, and a stable node tip across the read. Missing, inconsistent, extended, delivered, partially released or unavailable evidence leaves the whole batch locked. A node outage returns a retryable 503.

One SQLite transaction writes immutable release evidence and changes both the parent and all item locks to RELEASED. The old purchase cannot be reserved again; a new reviewed quote and purchase ID are required. Original publication records, purchase artifacts, signed bundles, validator signatures and replay tombstones are retained. An additive release table supplies a current-coin cursor. The API rechecks that coin and its timeout lineage; each validator independently verifies the canonical timeout parent without trusting the API cursor. Delivery lineage uses the actual reservation input, including a released successor.

The timeout observer rechecks service authorization, the minting-write ceiling and the purchases gate immediately before the atomic commit. The commit compares the complete parent and item snapshot that was checked. A concurrent confirmation or payment update leaves the new state intact and requires a fresh proof attempt. Repeated terminal observations validate the retained recovery receipt without requiring the released successor to remain unspent forever.

## Retained status and customer observation

`GET /protocol/native-purchases/inventory/{purchase_id}` is service-token protected and remains readable while sales are closed. One SQLite snapshot reads the parent, ordered items and decoded recovery receipts. The response binds the retained offer content hash, canonical purchase/batch IDs and hashes, vault, instance, rail, quantity and ordered deeds. It validates the state-specific transaction fields and recovery receipts, and omits signatures, spend bundles, full evidence and provider messages.

`observerEnvironment`, `network` and `adapterVersion` identify the observing service. `releaseIdentity` is the retained genesis artifact hash; deployment launcher IDs also come from the retained offer. Historical offers did not retain their runtime environment or source SHA set. Do not treat the observer environment as proof of historical environment, or use a status response as capability activation evidence. Reads do not require a live quote, current credential, active release or currently unspent successor.

The owner-authorized backend exposes `GET /protocol/purchase-intents/{id}/inventory` and `POST /protocol/purchase-intents/{id}/recover-inventory`. POST accepts only an empty object. It tries the existing timeout observer first, then the independently verified V2 authorization-expiry observer only after a conflict for PREPARED/SUBMITTED. Ownership, immutable identity and the sales gate are checked before each POST and after the final read. Authentication errors, missing records and provider outages do not trigger fallback. Neither method calls reserve, sign, submit, timeout-resume, payment or refund operations. Mutable payment/delivery progress may continue during a read.

`recoveryReceipt.kind` distinguishes `timeout-release` from `authorization-expiry`; release confirmation height is separate from the original reservation confirmation. Recovered inventory is not a refund or delivered holding. Retry requires a new reviewed purchase and quote. The earlier source's V1 puzzle execution failure remains historical evidence; versioned V2 support and existing expiry/timeout submission mechanisms are separately governed. This brick does not establish scheduler operation, customer signed outcomes, browser integration or launch readiness.
