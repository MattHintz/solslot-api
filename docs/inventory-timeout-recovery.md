# Inventory timeout recovery

`POST /protocol/native-purchases/inventory/reconcile-timeout` accepts only a purchase ID and requires the existing server token, minting-write ceiling and purchases operation gate. It observes an already executed timeout; it does not sign or broadcast a release. No request may supply its own chain evidence.

The reconciler reconstructs each exact reservation and timeout spend from the retained purchase artifact, signed bundle, item commitments and expiry. It requires a synced node on the purchase network, three confirmations, matching creation/spending heights, the exact canonical source spend and the matching timeout release (allowing only its uncommitted 32-byte buyer nonce), every unspent available successor, and a stable node tip across the read. Missing, inconsistent, extended, delivered, partially released or unavailable evidence leaves the whole batch locked. A node outage returns a retryable 503.

One SQLite transaction writes immutable release evidence and changes both the parent and all item locks to RELEASED. The old purchase cannot be reserved again; a new reviewed quote and purchase ID are required. Original publication records, purchase artifacts, signed bundles, validator signatures and replay tombstones are retained. An additive release table supplies a current-coin cursor. The API rechecks that coin and its timeout lineage; each validator independently verifies the canonical timeout parent without trusting the API cursor. Delivery lineage uses the actual reservation input, including a released successor.

This is partial recovery infrastructure, not completed PAYMENT-INV-1 remediation. There is no automatic scheduler, wallet release submission or customer outcome evidence in this change. Expired reservations whose original signed input never confirmed remain held: API-only expiry would leave both possibly broadcast authorizations and validator uniqueness/replay policy unresolved. No wall-clock TTL frees a signed reservation.

A new local execution gate reproduces a failure of the unchanged available-inventory v1 puzzle on both the original and replacement reservation, while its timeout-release spend executes. Existing construction-only tests did not cover that execution. Full transaction readiness remains blocked; preserve old puzzle bytes and use a separately coordinated, versioned protocol repair. See the draft10 release packet for exact source identities and evidence. No deployment, network transaction or beta enablement is implied.
