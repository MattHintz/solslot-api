# Bounded customer wallet-offer validation

Candidate change for PAYMENT-CPU-1. Applies to native XCH/CAT purchases, XCH
vouchers and both Sols swap directions. No protocol puzzle, transaction authority,
fee rule, network gate or deployed service is changed by this document.

Customer offers are decoded into raw spend records without executing their
puzzles. Encoding and raw data each have a 2,000,000-byte/character ceiling.
Compressed streams must finish exactly, with no extra/truncated stream or
unconsumed input. Supported compression dictionaries and uncompressed bundle
encoding remain accepted. Input counts are checked before Rust bundle allocation.
Puzzle hashes must match their coins; duplicate inputs fail.

Native payments require one positive real input and one requested-payment
carrier per deed, up to the existing 100-deed limit. Carriers have zero parent and
amount; their asset IDs must match the current purchase. Duplicate assets,
improper lists and oversized payment/memo data fail. Carriers are not executed
as real spends. XCH vouchers require one real input and no carriers.

Only the standard XCH and plain CAT spend templates returned by preparation are
admitted. The standard puzzle is reconstructed from its synthetic public key.
The solution must contain a literal quote of bounded conditions, with NIL outer
arguments; hidden-puzzle and arbitrary delegated-program variants are rejected.
CATs additionally bind the authorized asset, canonical inner puzzle, complete
parent lineage and the exact one-input ring. Custom wallet scripts that were
never generated by preparation must not be sent to these completion endpoints.

A fresh private subprocess performs submitted-offer parsing, structural checks,
condition-cost preflight, Offer construction, native payment semantics and wallet
signature verification. The real payment has one aggregate 100,000,000 preflight
allowance including condition charges. Every exception or exceeded final charge
terminates admission before Offer construction. Native aggregate construction
and voucher offer validation also run in this bounded process path. There are at
most two concurrent jobs per API event loop. Queue, startup and work share a
20-second job deadline; timeout and outer request cancellation kill and reap the
child. Linux adds 15 CPU seconds and 2 GB address-space limits. The existing
whole-request middleware deadline still covers the combined journey.
Cleanup independently owns pending startup and reaping, and retains its
concurrency slot across repeated cancellations until the child has been reaped.

Worker IPC is generated by the API and its exact local executable, over private
stdin/stdout pipes, with a 16 MB limit. Wallet strings are values inside those
locally generated messages; public endpoints do not accept IPC packets or job
names. Explicit native-byte reducers restore already evaluated Offer caches
without invoking its constructor in the API process. Never connect the IPC
decoder to a client, object store, upload or provider response. The API and
worker must use the same pinned source and locked Chia environment.

For Sols swaps, submitted records supply a coin identifier only after bounded
non-evaluating decoding. The API loads current chain context and reconstructs
the expected offer itself. Exact decoded bytes must match that offer before use.
Reverse BLS completion follows the same comparison; reverse EVM completion
continues to reject a wallet offer. Submitted/confirmed operation retries retain
their existing status-only path. Final swap signature checks run in the worker.

Tests use synthetic keys, local ledgers and simulated nodes. Validating or
constructing a 100-deed offer is not a provider acceptance, input-index capacity,
on-chain holdings or signed live-outcome claim. No service or wallet is activated
by this patch. Independent review and the complete release gates remain required.
